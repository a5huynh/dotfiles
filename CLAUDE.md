# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Install

Fresh machine, in order:

```sh
# Install `just` first — either via Homebrew (needs brew already) or directly:
curl --proto '=https' --tlsv1.2 -sSf https://just.systems/install.sh \
  | bash -s -- --to /usr/local/bin

just bootstrap                 # install Homebrew if missing, then brew bundle
just install                   # symlink dotfiles into $HOME
just bootstrap-plugins         # install fish/vim plugins
```

Or do one tool at a time: `install-{fish,vim,git,zed,zellij,claude,pi,herdr}` for symlinks, `bootstrap-{fish,vim,herdr}-plugins` for plugin managers, `bootstrap-herdr-integrations` for herdr agent hooks.

The plugin step **must** run after `install` — fisher reads `~/.config/fish/fish_plugins` and vim reads `~/.vimrc`, both from `$HOME` (via the symlinks `install` just created). `bootstrap-vim-plugins` also clones Vundle itself if missing.

All `install-*` recipes are idempotent — they **skip if the target path already exists**. The flip side is that a *real* file or directory sitting at a target silently wins forever: the recipe reports "already exists, skipping" on every run, and the tracked copy is dead weight that edits never reach. This had happened to the `github` pi skill, which sat in `~/.pi/agent/skills/` as a plain directory (identical in content, so nothing looked wrong). When adding something to this repo that already exists in `$HOME`, move the original aside first, then run the recipe, and `ls -la` the target to confirm it came out a symlink. `bootstrap` is also re-runnable. `bootstrap-plugins` is safe to re-run but does network I/O each time. Recipes call the internal `_link` helper (just `ln -s` with a skip-if-exists guard); edits to individual files go live immediately because the dotfiles are symlinked, not copied.

`install-zed` and `install-zellij` symlink individual files (`settings.json` + `themes/` for Zed; `config.kdl` + `layouts/` for Zellij) rather than the whole `~/.config/{zed,zellij}/` directory — both apps write runtime state (Zed: `conversations/`, `prompts/`; Zellij: `plugins/` with downloaded WASM binaries) into those directories and we don't want it leaking into the repo. `install-claude` follows the same pattern for `.claude/hooks/zellij-tab-notify.sh` and also loops over `.claude/skills/*/` to symlink the skills we author ourselves (currently `pr`, `review`, and `review-pr`, plus the `hig`, `plane`, and `worktrunk` symlinks into `.pi/`) into `~/.claude/skills/` — `~/.claude/` is full of runtime state and other unversioned hooks, and `~/.claude/skills/` in particular mixes an externally-managed collection (`xcode/`) and brew-owned skills (`peon-ping-*`), so we only symlink our own. `install-pi` symlinks `.pi/agent/AGENTS.md` (global agent instructions), every skill directory under `.pi/agent/skills/` (currently `herdr`, `socratic-tutor`, `github`, `dnsimple`, `plane`, `hig`, and `worktrunk`), and every extension under `.pi/agent/extensions/` (currently `todo-md.ts`, `session-title.ts`, `recap.ts`, `petdex.ts`, `next-prompt.ts`, and `border-status-editor.ts`) into `~/.pi/agent/`, which otherwise holds runtime state (`auth.json`, `sessions/`, other unmanaged `skills/` and `extensions/`, `themes/`). The recipe loops over `.pi/agent/skills/*/` and `.pi/agent/extensions/{*.ts,*/}`, so tracking a new pi skill or extension is just dropping a `<name>/SKILL.md` dir or a `<name>.ts` file into the repo — no justfile edit needed (the `_link` skip-if-exists guard keeps it idempotent). The extension loop is deliberately scoped to files present in *this repo*: `~/.pi/agent/extensions/` also holds `herdr-agent-state.ts` (generated by herdr, see below) and other unversioned extensions, which must not be clobbered. `install-herdr` symlinks only `.config/herdr/config.toml` — `~/.config/herdr/` also accumulates runtime logs (`herdr.log`, `herdr-client.log`, `herdr-server.log`).

`.config/herdr/plugins/tab-jump/` is a herdr plugin (herdr ≥ 0.7.4 has a plugin system: `herdr plugin link|install|list|action|pane`, manifest `herdr-plugin.toml`) that replaces the zellij `room.wasm` binding — fuzzy-search every tab in the session and jump to it. `just bootstrap-herdr-plugins` registers it; the recipe loops over `.config/herdr/plugins/*/` and skips anything already in `herdr plugin list`, so adding a plugin is just dropping a `<id>/herdr-plugin.toml` dir into the repo. Unlike everything else here it is **not** symlinked — `herdr plugin link` writes the absolute path into `~/.config/herdr/plugins.json`, so the registration points straight at this repo and edits to `jump.sh` are live. The manifest's `id` must match the directory name for the bootstrap recipe's skip-check to work.

The plugin has two halves: a `[[panes]]` entrypoint (`placement = "popup"`, a session-modal float that leaves the workspace layout alone — the analogue of zellij's `floating true`) and a `[[actions]]` entrypoint that opens it, bound to `prefix+y` in `config.toml` via `[[keys.command]]` with `type = "plugin_action"`. The key can't point at the pane directly; `plugin_action` is the only plugin-aware keybind type, so the action shells out to `herdr plugin pane open`. `[[keys.command]]` blocks must stay at the *end* of `config.toml` — TOML would fold any later bare key into the command table instead of `[keys]`. Commands reach their own files through `$HERDR_PLUGIN_ROOT` rather than a hardcoded path, and the `herdr` binary through `$HERDR_BIN_PATH`.

`jump.sh` reads one `herdr api snapshot` and renders a row per tab (agent status dot, `<workspace#>.<tab#>` quick-jump token, `workspace › tab`, the agent's terminal title, cwd), pipes it through `fzf` with a live `herdr pane read` preview, then focuses the choice. Rows are sorted by **agent priority** by default — `blocked` → `done` → `working` → `idle` → unknown, which is the same "wants your attention" ordering `tab-status` marks in the tab bar — and `ctrl-s` cycles through four orders: `status`, `position` (workspace #, then tab #), `name`, and `cwd`. `TAB_JUMP_SORT` pins the initial one. Every order tie-breaks on workspace/tab number, so the list is stable across reloads and a workspace stays contiguous inside a status group. Note that `position` is a real sort rather than the identity: `api snapshot` returns tabs in **no particular order** (a workspace's tabs come back as e.g. `8, 1, 2, 15, 12`), so the original picker, which did no sorting at all, listed them apparently at random. Two things make the sort cycle work without any persistent state. `ctrl-s` is bound to fzf's `transform` action, which runs `jump.sh --cycle`, reads the **current prompt** back out of `$FZF_PROMPT` (fzf exports it to child processes) to learn the active order, and emits `reload(...)+change-prompt(...)` — so the prompt *is* the state, and there is no lockfile or scratch file to leak or go stale; keep the emitted `change-prompt` string in sync with `--prompt`, since `--cycle` parses it back. And `reload` re-invokes the script rather than re-sorting the rows fzf already holds, which means changing the sort also refetches the snapshot — `ctrl-s` doubles as a refresh of the *list*, where `ctrl-r` refreshes only the *preview*. `TAB_JUMP_SNAPSHOT=file.json` feeds it a canned snapshot (mirroring `tab-status`'s override) so the sort logic is testable offline against statuses that are hard to catch live, which is how the `blocked` ordering was checked. The preview is bottom-anchored so it shows what the tab was *last* doing: fzf always renders a preview from its first line and has no "scroll to end", so the trick is to feed it exactly as many lines as the window is tall via `tail -n $FZF_PREVIEW_LINES` (fzf exports the window's true height). `nowrap` on the preview window is part of that mechanism rather than cosmetic — with wrapping on, one long line occupies several rows and pushes that many lines of the newest output back off the bottom. Two non-obvious constraints. The tab and pane ids ride along as hidden TSV fields (`--with-nth=1`) because the visible text is unstable. And the `herdr tab focus` call must happen *after* the popup is torn down — the teardown restores focus to the previously active pane, which would undo the jump — so it runs in a backgrounded child guarded by **`set -m`**. That is load-bearing: a plugin pane's process is a session leader and herdr kills its entire process group on close, so a plain `... &` from a non-interactive shell stays in that group and is killed before it ever runs (this silently broke the first version — the picker worked, selection parsed, nothing jumped). Job control is what puts the child in its own process group. The child also *verifies* rather than retrying on error, since `tab focus` returns success even when the teardown immediately steals focus back.

A plugin pane's stderr dies with its pty and never reaches `herdr plugin log list` (that only captures `[[actions]]`), so `jump.sh` has an opt-in trace: `herdr plugin pane open --plugin tab-jump --entrypoint picker --env TAB_JUMP_DEBUG=1` writes a `set -x` log to `$TMPDIR/tab-jump.log`. Note that a popup opened with `--no-focus` is keyboard-inert but still occupies the single popup slot, so subsequent opens fail with `popup already open`; plugin panes are invisible to `herdr api snapshot` and `pane list`, and `plugin pane open` does not return their id, so the only way to clear a wedged one is to `kill` the `jump.sh` pid from `ps`. herdr's own `goto` (`prefix+g`) covers similar ground but enumerates every pane, which is too noisy. (That parenthetical about `plugin log list` is true only of `[[panes]]`: `[[events]]` and `[[actions]]` are both captured, events with an `event` field and no `action_id`.)

`ctrl-t` in the picker **sends the highlighted tab to another workspace**, which herdr cannot do natively: there is no `tab move`, only `pane move` (the `move_tab_previous`/`move_tab_next` keys only reorder within a workspace). A second fzf stage lists the other workspaces plus `+ new workspace`, and typing a name that matches nothing creates a workspace with that name (`accept-or-print-query`: a lone output line is the query, a second line is a picked row). The picker then loops back to the refreshed list with the result on top, so several tabs can be sent in one go. The work is in `move.sh <tab_id> <workspace_id|--new [LABEL]>`, which replays the tab one pane at a time. Its layout tree comes from **`layout.export` over the socket** (`nc -U $HERDR_SOCKET_PATH`, one JSON line, read-only) because the CLI has no `layout export` and `pane layout` flattens the splits into a list that cannot be turned back into a tree; if that fails the panes are placed side by side rather than the move being refused. The replay works because a split node's region is always held by its **first leaf**: move the root's first leaf with `--new-tab`, then walk pre-order, splitting `leaf(first)` to place `leaf(second)`, so every split lands inside a region that already exists. Ratios carry over unchanged, since both `layout.export` and `pane move --ratio` give the *first* pane's share (verified by round-tripping a nested 0.3/0.6 tree); pane labels and zoom are restored after. Four traps. A moved pane gets a **new id**, so every later split targets the remapped one, read from `.result.move_result.pane.pane_id`. **herdr refuses to move a pane out of a zoomed tab but answers success** (`changed: false`, `reason: "zoomed_tab"`, with the pane echoed back where it was) so `move.sh` treats `changed: false` as failure and unzooms any multi-pane source first; trusting the returned pane id alone made the first version report a three-pane move that never happened. **Moving the last pane out of a workspace closes it** (`closed_workspace_id`), so the picker warns when the tab is its workspace's only one. And a tab-status marker stays on the moved tab's label (`pane.moved` is not a tab-status trigger, so stripping it would leave a done tab unmarked) but is stripped from a workspace name defaulted from it, using the same glyph list as `unmark`, which makes that a coupled *trio* with `GLYPHS`. `move.sh --dry-run` prints the commands and touches nothing, and `TAB_JUMP_SNAPSHOT` plus `TAB_JUMP_LAYOUT=file.json` (a `layout.export` response) make it testable offline.

`.config/herdr/plugins/tab-status/` puts a marker on the tab bar for agents that want your attention, because herdr has no tab-bar status indicator and no way to configure one — the only `[ui]` tab-bar keys are `hide_tab_bar_when_single_tab` and `tab_bar_position`, and the `rows`/`row_gap` token templating exists solely under `[ui.sidebar.*]`. So the marker has to live in the tab **label** itself, via `herdr tab rename`, which is the same trick `.claude/hooks/zellij-tab-notify.sh` plays on zellij. `mark.sh` reads one `herdr api snapshot` and reconciles every tab: prefix `▲` when the tab's aggregated `agent_status` is `blocked`, `✓` when it is `done`, nothing otherwise. It marks **both** states because that is herdr's own notion of attention (its toast fires when an agent "finishes or is blocked") and because `done` is by far the more common of the two — marking only `blocked` produces a feature that almost never lights up. `jump.sh` draws the same two states in the picker (`▲` blocked, `✓` done) and *strips* a leading marker back off the label when rendering (`def unmark`), so a marked tab does not show its glyph twice — once in the picker's status column and once inside the label text the marker was written into. That strip is presentation-only — `jump.sh` never renames — so the two plugins cannot oscillate, but it does mean `GLYPHS` here and `unmark` there are a **coupled pair** that must be extended together. It earns its keep beyond cosmetics: it returns two columns to the 34-char name field, and it stops the picker's `name` sort from clustering every marked tab under `▲`/`✓` instead of sorting them by name. The **focused** tab is never marked: `done` fires every time an agent finishes a turn, so the tab you are actively reading would wear a marker almost permanently and drown out the tabs that actually want you.

The marker cannot be coloured, and the alternatives are all dead ends worth not re-testing. Escape sequences survive `herdr tab rename` and round-trip through `api snapshot` intact, but the tab bar renders them **literally** — `\033[31mANSI\033[0m` draws as `[31mANSI[0m`. There are no tab-bar theme tokens either (the palette is fixed: `accent`, `panel_bg`, `surface0/1`, `surface_dim`, `overlay0/1`, `text`, `subtext0`, `mauve`, `green`, `yellow`, `red`, `blue`, `teal`, `peach`), and the only `[ui]` tab-bar keys remain `hide_tab_bar_when_single_tab` and `tab_bar_position`. Inherently-coloured emoji (`🔺`/`✅`) are the one route that would work, rejected because they occupy 2 cells in a row herdr draws itself. Embedding escapes would also bleed: `jump.sh` wraps `workspace › tab` in its own colour spans, and a `\033[0m` inside a label would terminate them early and corrupt the picker's columns.

It is driven by `[[events]]` on `pane.agent_status_changed`, `tab.focused` and `workspace.focused`, so there is no daemon of ours — herdr invokes the script. The two focus hooks exist because of the focused-tab suppression above: without them a marker would linger on a tab you are already reading until its agent next changed state. `workspace.focused` is needed separately because switching workspace moves `focused_tab_id` without necessarily firing `tab.focused`, which would leave the tab you just navigated away from unmarked while it still wants attention. Redundant triggers are harmless — the reconcile is idempotent and the lock coalesces. Event hooks take a `command` and **cannot** reference an `[[actions]]` id, so the command is duplicated between the two blocks; the action is kept purely as the manual entrypoint (`herdr plugin action invoke sync`). Four things are load-bearing. Labels are always re-derived from a live snapshot and **never cached**, so a tab you rename mid-session keeps its new name. The reconcile is strip-then-maybe-prefix, making it idempotent and convergent in one pass — it cannot double-mark, and it swaps `✓`→`▲` correctly when a done agent becomes blocked. `GLYPHS` (the strip set) is deliberately **independent** of `MARKS` (the add set): deriving one from the other means `TAB_STATUS_MARKS='{}'` has nothing to strip with, silently breaking the uninstall path — markers live in labels, so unlinking the plugin without stripping first strands them there forever. And in the jq, `[$prefixes[] | . as $p | select($label | startswith($p)) | $p]` needs that explicit `. as $p`; a bare `startswith(.)` resolves `.` to the *piped input* (`$label`), so every label matches itself and the script amputates the first two characters of every tab name in the session. That last one was caught only by `--dry-run`, which is why it exists.

A coalescing `mkdir` lock (with a stale-pid steal and a rerun flag) serializes bursts — 20+ agents changing state fire a lot of events, and overlapping renames would fight. `mark.sh --dry-run` prints what it would do and touches nothing; `TAB_STATUS_SNAPSHOT=file.json` feeds it a canned snapshot so the marking logic is testable offline with no herdr and no network; `TAB_STATUS_DEBUG=1` writes a `set -x` trace to `$TMPDIR/tab-status.log`; `TAB_STATUS_MARKS='{}'` strips every marker for a clean uninstall.

`.config/herdr/plugins/space-agents/` puts the number of agents open in each workspace on that workspace's sidebar row, because herdr has no built-in token for it — the space-row built-ins are exactly `state_icon`, `state_text`, `workspace`, `branch`, `git_status`, and while `WorkspaceInfo` does carry `pane_count` and `tab_count` over the API, neither is exposed to the row layout and neither counts *agents* anyway. The supported escape hatch is **workspace metadata**: values reported through `herdr workspace report-metadata --token NAME=VALUE` render as a `$NAME` token in a row layout (the mechanism the bundled config advertises as `$jj_status`), so `count.sh` reads one `herdr api snapshot`, counts `agents[]` per `workspace_id`, and reports `agents=·N`; `config.toml` renders it as `$agents`. That is the whole reason this is a plugin and not two lines of config.

The marker was `·N` until herdr 0.9 and is now a **bare number colored by threshold** (see the upgrade note below). It was never a status glyph because herdr's vocabulary (`◉` blocked, `●` done, `○` idle) is entirely *status* marks — `●` already means "done" both in herdr and in `tab-jump/jump.sh`, so reusing it would claim a state rather than a quantity. There is no "agent" glyph to borrow, and an emoji would cost 2 cells of a 32-column sidebar (the same width constraint that shapes `tab-status`). A workspace with **no** agents reports no token rather than `0`: most spaces are plain shells, and a column of zeroes buries the counts that matter.

Four things are load-bearing. It is deliberately **not** hooked to `pane.agent_status_changed` — the busiest event herdr emits, and one that cannot change a count; the four hooks (`pane.agent_detected`, `pane.closed`, `pane.exited`, `pane.moved`) are the only things that move an agent in or out of a workspace, with `pane.exited` there because a dead process drops out of `agents[]` while keeping its pane, and `pane.moved` because it is the only one that changes two counts at once. `[[startup]]` is needed separately because workspace metadata is display-only **runtime** state that does not survive a server restart or session restore — event hooks are repair-on-change, so without it a restored session would show no counts until an agent happened to come or go. The desired value is **diffed against the token already in the snapshot** (`api snapshot` reports each workspace's current `tokens`), so unchanged workspaces emit nothing; without that, every pane event would rewrite identical metadata for every workspace, one socket round-trip each. And there is **no `--ttl-ms`** anywhere: a TTL (24h max) would make the count silently vanish from a workspace that simply had not changed recently, so `count.sh --clear` is the uninstall path instead — though unlike `tab-status`, nothing is stranded in user data if the plugin is unlinked, since these tokens live in herdr's runtime state rather than in a label, and the `$agents` token just renders empty.

`count.sh --dry-run` prints the metadata writes it would make and touches nothing; `SPACE_AGENTS_SNAPSHOT=file.json` feeds it a canned snapshot so the counting logic is testable offline with no herdr; `SPACE_AGENTS_DEBUG=1` writes a `set -x` trace to `$TMPDIR/space-agents.log`; `SPACE_AGENTS_PREFIX` re-adds a prefix, which costs the threshold colors — any non-numeric character makes every `gt`/`lt` rule fail to match and the token falls back to its base `fg`. The offline fixture is worth keeping around — it covers an agent with a **null** `workspace_id` (a pane outside any workspace), which `from_entries` would choke on as a key.

**This was done on herdr 0.9.1.** 0.9 adds value-based styling to sidebar tokens (#3693), which applies to metadata tokens and so to `$agents`: `RawStyledSidebarToken` gains a fifth field, `rules`, a list of at most 16 entries each taking **exactly one** of `equals`/`contains`/`starts_with`/`gt`/`lt` plus `ignore_case` (text conditions only), `fg`, `bold`, and `dim` — and also `hide`, which the error strings do not mention but `config check` accepts. None of it appears in the bundled config template; the schema is only recoverable from the binary's validation error strings (`sidebar rule requires exactly one of equals, contains, starts_with, gt, lt`, `sidebar rules require a text-valued token`, which is what rejects `rules` on `state_icon`, and `sidebar tokens may contain at most 16 rules`). The space-row built-ins are **unchanged** through 0.9.1 — `pane_count` and `agent_count` are both rejected in a space row as `unknown sidebar token; custom tokens must start with `$`` — so the plugin is not obsoleted by the upgrade; agent rows do gain a `machine` token.

So `count.sh` now emits a **bare number** and `config.toml` carries `rules` that color it (`gt = 5` red, `gt = 2` yellow, dim below that). The `·` had to go because `gt`/`lt` are **numeric** and `·7` does not parse as one — the rules are accepted by the validator and then silently never match. Threshold colors do the disambiguation the `·` existed for (see the `PREFIX` comment in `count.sh`) and hand back a column of a 32-wide sidebar. Rules are ordered **highest threshold first** and the **first match wins** — confirmed by observation (a workspace of 8 rendered red, not yellow), since the precedence is not recoverable from the binary. That ordering is load-bearing: a count of 7 satisfies both `gt = 5` and `gt = 2`, so reversing them would make the red rule unreachable and every busy space would read yellow. Three traps guard all this. A malformed rule — zero conditions or two — is a **file-level** TOML error, reported as `data did not match any variant of untagged enum RawSidebarToken` plus `; using defaults`, which discards *every* customization in `config.toml`, not just the offending token. 0.8 rejects the `rules` key exactly the same way, so because `~/.config/herdr` is a symlink to this repo, committing rules before every machine is upgraded would silently reset herdr to stock defaults on the stragglers. And migration is free only because the reconcile **diffs against the token already in the snapshot**: every workspace still showing `·N` differs from its new bare `N` and is rewritten once, so the old markers are not stranded.

**The count cannot be right-aligned**, and the dead ends are worth not re-testing. There is no alignment control in the schema — `align`, `justify` and `min_width` are all rejected on a sidebar token, and the row layout is left-packed with the count following a variable-width workspace name, so alignment would have to come from the *value*. It cannot: herdr trims the metadata value, and every width-bearing pad character is Unicode `White_Space` and therefore stripped (`U+00A0` and `U+2007` both round-trip to length 1), while the characters that survive (`U+2060` word joiner, `U+180E`) are zero-width and pad nothing. A leading `U+2060` does make following spaces *interior* and they do survive the trim (`[8288, 32, 32, 49]`), but even then true right-alignment is unreachable, because the sidebar auto-scales its width between `sidebar_min_width` and `sidebar_max_width` and can be resized or collapsed at any time, while metadata is only recomputed on pane events — so the padding would be stale and visibly wrong much of the time.

The herdr↔agent state integrations (pi/claude/codex lifecycle hooks that report `idle`/`working`/`blocked` and enable native session restore) are generated *outside* this repo by herdr, so they're not symlinked. Run `just bootstrap-herdr-integrations` to (re)install them via `herdr integration install` — safe to re-run, and it re-syncs versions after a herdr upgrade (`herdr integration status` shows current/outdated). herdr and pi are not in the Brewfile yet, so a fresh machine needs them installed first.

These go stale silently — nothing warns you, and `status` is the only place it shows. pi sat on v5 against v8 for a while. Worth diffing the old file against the new one after an update (`cp` it aside first; `install` overwrites in place), because the integration is a working example of how herdr expects an agent to be driven and its changes carry lessons. The v5→v8 rewrite *deleted* ~120 lines: v5 listened to `agent_end` and needed a retryable-error regex, a retry grace hold and an idle debounce to avoid reporting a false `idle` between provider retries, while v8 listens to **`agent_settled`** ("no automatic retry, compaction, or queued continuation will run") plus `ctx.isIdle()` and needs none of it — so the env knobs `HERDR_PI_IDLE_DEBOUNCE_MS` and `HERDR_PI_RETRY_GRACE_MS` no longer exist. It also dropped `session_shutdown`/`pane.release_agent` and gained Windows named-pipe support.

The v8 change worth carrying into our own extensions is the gate: `ctx?.hasUI !== true` became **`ctx?.mode !== "tui"`**. pi's own types say `hasUI` is "true in TUI **and RPC** modes" and to "use `tui` to guard terminal-only UI" — so `hasUI` does not mean what it looks like it means, and anything touching the terminal must gate on `mode`. In RPC mode `ctx.ui.setTitle` does not write a title at all; it marshals one into an `extension_ui_request` JSON line on the protocol stream. `session-title.ts` was written against `hasUI` and corrected to `mode` after this update, with a regression test that asserts an RPC session is left alone.

`.pi/agent/extensions/todo-md.ts` is a pi extension giving each agent a task list backed by a plain markdown file. It registers a `todo` tool (`list`/`add`/`start`/`toggle`/`remove`/`clear_done`), a `/todos` overlay (plus `/todos sessions|hide|show`), and an always-on widget above the editor. It is a file-backed rewrite of pi's bundled `todo.ts` example (`$(brew --prefix)/lib/node_modules/@earendil-works/pi-coding-agent/examples/extensions/todo.ts`), which stores state in session entries instead; that makes the bundled version rewind correctly when you branch a session, but it does not survive a resume, which is the whole point here. Non-checkbox lines (headings, prose, notes) round-trip verbatim and new items are inserted after the last existing checkbox, so the file stays hand-editable. Ids are positional and shift after `remove`/`clear_done`, so every tool result returns the refreshed list. Extensions in `~/.pi/agent/extensions/` are auto-discovered and hot-reload with `/reload`.

The list is **per session**, not per repo: `~/.pi/agent/todos/<project-key>/todo-<sessionId>.md`. Several agents in one repo would otherwise trample a single shared file, and a list keyed by session id is runtime state — meaningless to anyone who clones, and in-repo it would cost a `.gitignore` rule per project (the same reasoning that keeps the `hig` cache in `$TMPDIR`). `<project-key>` is pi's own workspace encoding (`--Users-me-work-repo--`), so a project's todo files sit under the same name as its transcripts; it is keyed off the **git root** rather than `cwd`, so sessions started in a subdirectory share a bucket while each worktrunk worktree gets its own. A list that empties deletes its file and reclaims the bucket, and a session pi is not persisting (`pi --no-session`) has nothing to key a file to, so it stays in memory. `scope: "project"` in the config restores the old single `<git-root>/todo.md`, and `PI_TODOS` overrides everything per run: `off` for memory only, a bare name for a shared list at `~/.pi/agent/todos/shared/<name>.md` (two agents deliberately coordinating), or a path. Anything but a session file can be raced by another agent, so those writes take a `mkdir` lock with a stale-owner steal, and every write lands through a temp file and `rename` so a concurrent reader never sees half a list. Waiting out the lock proceeds **unlocked** rather than failing — losing the user's item is worse than an interleaved write. Two traps live here: `save()` must count remaining items from the *serialized text*, since `file.todos` was parsed before the caller edited `file.lines` and reads as empty on a first `add` (which made every new session file delete itself instead of being written); and the lock must `mkdir -p` the parent first, or the first shared write spins forever — `mkdir` fails with ENOENT, `stat` fails too, and a missing lock reads as a stale one to be stolen and retried.

The widget is modelled on [pi-tasks](https://github.com/tintinweb/pi-tasks): a `● 5 todos (2 done, 1 in progress, 2 open)` header, `#N` ids, `✔`/`◼`/`◻` status glyphs, strikethrough on completed rows, and a star spinner with an elapsed clock on whatever is in progress. Markdown gets a third state from `- [/]` (`[-]` and `[~]` are read the same way). Elapsed time is measured from when the extension **first saw** an item in progress, not from a stored timestamp: writing one into a file the user hand-edits is worse than a clock that restarts on resume. The spinner's `setInterval` belongs to the widget component and is cleared in its `dispose()` — pi disposes the outgoing widget on every `setWidget`, so recreating the component per refresh cannot leak timers, and it is `unref()`d so a stray one can never hold the process open. Render caching is off while anything is in progress, since the clock and the spinner move on their own. Display is configured by `~/.pi/agent/todo-md-config.json` merged key-by-key with `<git-root>/.pi/todo-md-config.json`: `scope`, `sortOrder` (`id`/`status`/`active`), `collapseCompleted`, `maxVisible`, `showAll`, `hiddenAt`, `hideWhenComplete`, `glyphs`. Config is data, never code, and every value is validated and falls back on its own — a `.pi/` that arrived with a cloned repo must not be able to break the widget or (via a glyph carrying `ESC ]0;…`) steer the terminal.

`node .pi/agent/extensions/todo-md.test.mjs` runs the whole extension offline — no pi host, no network, no model. It transpiles the TypeScript with the esbuild inside pi and imports it into a sandbox whose `node_modules` symlinks pi's own packages, then fakes everything the host provides (`pi.exec`, the session manager, the TUI, the theme), which is what makes the widget's own rendered lines assertable. Both bugs above were caught by it. The harness lives beside the extension but is deliberately a `.mjs`: `install-pi` globs `*.ts` and `*/`, so it is never symlinked into `~/.pi/agent/extensions/` where pi would try to load it. One trap when extending it — a host option must be passed as `null`, not `undefined`, to mean absent, since a destructuring default fills `undefined` back in.

`.pi/agent/extensions/session-title.ts` writes the session's **task** into pi's terminal title, so herdr's sidebar and tab picker can say what a pi pane is actually doing. herdr reads every pane's title into `terminal_title_stripped`, which both `[ui.sidebar.agents.rows_by_agent]` and `plugins/tab-jump/jump.sh` render — claude reports its task there ("Review pull request #871") but pi reported `π - <dirname>`, a restatement of the workspace the row already names, which is why pi was held to one sidebar row. Writing the *title* rather than herdr's own `pane report-metadata` is the load-bearing choice: the sidebar and the picker already read that field, so both light up with no change to either, where a `--token task=…` would have needed `config.toml` **and** `jump.sh` edited. The label is the session's **first** user prompt — it identifies a pane for its whole life, which is what you need when scanning 20 of them, and it does not churn the sidebar every turn (`PI_SESSION_TITLE=last` tracks the newest instead, `off` disables). An explicit session name always wins and the extension then does nothing at all, because pi already renders `π - <name> - <dir>` itself; fighting it would only flicker. The label is bare — no `π - ` prefix, no cwd — because the row prints workspace and tab beside it and `jump.sh` clips the field to 46 columns, and because that is the shape claude emits, which is the shape the sidebar was tuned for. Gated on `HERDR_ENV` so a pi started outside herdr keeps its own title, where the OS window title has no other "which agent is this" marker, and on `ctx.mode === "tui"` rather than `hasUI` (see the integration notes above — `hasUI` is also true over RPC, where a title is a JSON line, not a title). Four traps. The timing: pi calls its own `updateTerminalTitle()` *after* extensions bind (`rebindCurrentSession`), so a title set during `session_start` is silently clobbered — hence the delayed re-assert (`PI_SESSION_TITLE_DELAY_MS`). Control characters are stripped because the title is written inside an OSC sequence that a BEL or ST in the prompt would terminate early, dumping the rest of the prompt into the shell as literal text — reachable, since prompts routinely carry pasted terminal output. `truncateToWidth` measures wide characters correctly but wraps its ellipsis in **ANSI resets**, so its output is passed through `stripTerminalSequences`; escapes in a label would bleed into herdr, which renders labels literally and whose picker wraps this field in its own color spans (the same coupling that makes `tab-status`'s `GLYPHS` and `jump.sh`'s `unmark` a pair). And the file is deliberately **not** named `herdr-*`: `~/.pi/agent/extensions/` also holds herdr's generated `herdr-agent-state.ts`, and `herdr integration install pi` overwrites what it owns by name. `node .pi/agent/extensions/session-title.test.mjs` runs it offline against a faked host on the `todo-md.test.mjs` harness; the ANSI-in-ellipsis bug was caught by it.

`.pi/agent/extensions/petdex.ts` drives the [Petdex](https://petdex.dev) desktop pet from pi. Petdex Desktop (`cask "petdex"` in the Brewfile; an app already sitting in `/Applications` makes the install stop with "already an App", so take it over with `brew install --cask --adopt petdex` — which **quits** the running app, so relaunch it per the restart trap below) runs a hook server on `127.0.0.1:7777` — `POST /state` moves the pet, `POST /bubble` updates a per-session card in its "Flock" view — authenticated by a token it rotates into `~/.petdex/runtime/update-token` on every boot, so the token is re-read per post. The app wires its supported agents itself, but stock pi is not one of them (only the **OMP** fork is), so this is a port of the extension it generates for OMP, `packages/petdex-desktop-native/src/assets/omp-extension.ts` in `crafter-station/petdex`. pi's event API matches nearly one-for-one; the differences are `ui_prompt_start`/`ui_prompt_end` for OMP's `tool_approval_requested` (closed out with `request_id`/`resolves_request_id`), `agent_settled` for `agent_end` (the same reason herdr's v8 integration switched — no false "Done." between retries), pi's tool fields (`path`, `pattern`, `command`), and the `ctx.mode === "tui"` gate. OMP's session journal was dropped: the app replays it only for agents it reconciles natively, so for `pi` it is unread disk writes. The rest of the rework is for running a dozen sessions at once, which the upstream file does not consider, and three facts about the app drive it — all read from its Zig source, worth not re-deriving. The Flock holds **8** cards (`max_bubbles`) and evicts the **least recently updated**, which is precisely the session blocked on you, since a blocked session stops emitting events; so `waiting` is re-sent every 60s (`PI_PETDEX_WAITING_MS`). The heartbeat text carries the elapsed time (`Waiting on you · 3m`) and that is load-bearing: the server **suppresses a bubble identical to the previous one without bumping its recency** (`bubblePresentationEquivalent`), so a verbatim heartbeat refreshes nothing — verified live, where a changed text moved the counter and a repeat would not. The hook server's local budget is **30 req/s shared by every agent** and a 429 is silent, so a successful `tool_result` posts nothing and tool calls coalesce per session to leading + trailing within 250ms (`PI_PETDEX_COALESCE_MS`), while attention and lifecycle states — `waiting`, `failed`, `Done.` — are sent immediately and cancel anything queued, so a stale tool update can never land after them. And handlers are **fire-and-forget**, where OMP's awaited up to 300ms of network per event on pi's own loop; posts are chained per session so they still arrive in order. Timers hold the `Session` record, never a `ctx`. The card title is the **latest** prompt (`PI_PETDEX_TITLE=first` pins the first, as `session-title.ts` does for the sidebar), and that needs the bubble's `title_source` **omitted**: the app makes a `prompt` title sticky — it only fills a card that has none (`.prompt => slot.title_len == 0` in `hook_server.zig`) — so the first version, which sent `prompt`, showed its first prompt forever while only the subtitle moved, which read as a stuck card. `GET /bubble` cannot confirm this either way; it echoes the last request, not what the card shows. Inside herdr it sends `herdr_pane_id`, so clicking a card focuses the pane. Petdex also ships a herdr bridge plugin (`dev.petdex.bridge`, `herdr plugin install crafter-station/petdex/packages/petdex-desktop-native/integrations/herdr`) that mirrors herdr's coarse agent status into the pet for agents without direct hooks. It was trialled and **removed** along with the `bun` it needs, since this extension covers pi and gives tool-level detail the bridge cannot. If it is ever reinstalled, its config (`herdr plugin config-dir dev.petdex.bridge`/`config.json`) must carry `{"excludeAgents": ["pi"]}`: it keys pi cards by the session *file* where this extension keys by session *id*, so with both running every pi pane gets two cards. Restarting the app has a trap: its listener binds `:7777` with `reuse_address = false` and **never retries**, so relaunching while the old instance's connections are still in TIME_WAIT (~30s on macOS) starts it with **no hook server** — the pet renders, the token is not rotated, and the only sign is a `:7777 bind failed` debug print nobody sees. Wait for `petdex-desktop-native` (the process name; `Petdex` is only the app name) to exit and for `netstat -an -p tcp` to show nothing on `.7777` before reopening, and confirm with `curl http://127.0.0.1:7777/health`. Off switches: `PI_PETDEX=off` per run, Petdex's own `~/.petdex/runtime/hooks-disabled` for every agent at once; `/petdex` reports the connection. `node .pi/agent/extensions/petdex.test.mjs` runs it offline against a stub hook server and a temp runtime dir (`PETDEX_HOOK_URL`, `PETDEX_RUNTIME_DIR`), on the `session-title.test.mjs` harness; it takes ~14s because the heartbeat test needs whole-second intervals for the elapsed text to differ — at sub-second ones every beat reads `0s`, which is what the distinct-text assertion caught on its first run.

`.pi/agent/extensions/next-prompt.ts` ports Claude Code's **prompt suggestions** to pi: after each settled turn it predicts what you would type next and `border-status-editor.ts` shows it as dim ghost text in the empty editor, accepted with **Tab** or **→**. Claude Code runs this as a fork of the main conversation on the *main* model (found in the 2.1.280 binary: a `prompt_suggestion` fork with no model override, skipped when the main turn's prompt cache is cold), but `modelRegistry.complete()` builds its own request and cannot count on hitting the main loop's cache, so this sends a trimmed transcript (last 12 messages, plus the original request if it scrolled out) to **Haiku 5.5** instead — ~0.7s and ~$0.00002 a call. The prompt and output filter are ported from Claude Code's "Prompt Suggestion Generator v2" (2–12 words, no questions/evaluations/agent-voice, silence when unsure), plus its suppression after an errored or aborted turn. The split across two files is forced: pi allows exactly **one** custom editor and `border-status-editor.ts` owns it, so a second `setEditorComponent` would silently drop the status borders; the generator publishes `{text}` on `pi.events` channel `next-prompt:suggestion` (the string is duplicated in both files rather than imported), and without `border-status-editor.ts` nothing is shown. Tab/→ are only taken while the editor is empty, no autocomplete is open, and a suggestion is showing — otherwise they keep their meaning. Three traps. pi 1.0.4's catalog has **no Haiku 5.5**, and `registerProvider("anthropic", {models})` would *replace* every Anthropic model, so the model is synthesized from the `claude-sonnet-5-5` entry when the registry lacks it (the registry's own entry wins once pi ships one; `complete()` resolves the provider from `model.provider` and sends the object as given). Its `compat` is rebuilt rather than spread: Sonnet's `supportsMidConvoEffort` makes pi force adaptive thinking at effort `high` on every request. And Haiku 5.5 has adaptive thinking **on by default** with thinking tokens counted against `max_tokens`, so a 100-token budget can end after a thinking block with no text — the call passes `thinkingEnabled: false`, which pi only turns into `thinking: {type: "disabled"}` when `thinkingLevelMap.off` is not `null` (Sonnet's is, so the synthesized entry must not inherit it); a safety refusal arrives as `stopReason: "error"`, so anything but `"stop"` is silence. The suggestion is drawn into the editor line, so escapes are stripped and then C0/C1 controls, as in `session-title.ts`. A submit, a new turn, or typing during the call aborts it and drops the result. `PI_NEXT_PROMPT=off` disables it; `PI_NEXT_PROMPT_MODEL=provider/id` picks any model the registry knows. `node .pi/agent/extensions/next-prompt.test.mjs` runs both halves offline — the generator against a faked `complete()`, the ghost text against pi's real `CustomEditor`.

All pi extension event handlers must use the `ctx` passed *into* the handler rather than capturing one from an enclosing scope — pi invalidates `ctx` on session replacement and every getter on the stale object throws. `pi.on()` has no unsubscribe, so handlers outlive their session. `todo-md.ts` sidesteps this by only ever using the handler's own `ctx`; `border-status-editor.ts` has to work around it with a generation counter because it captures `ctx` for a custom editor component. That extension carries a second trap: it re-frames `super.render()` by swapping pi's top and bottom borders for status lines, but the stock editor appends the **autocomplete dropdown after its bottom border**, so treating the last line as the border silently drops the last suggestion and paints the status bar over it — which made `/skill:review-pr` look unregistered while `/skill:review` showed. It now splits the dropdown off using the editor's `renderedAutocompleteHeight`, which is `private` in pi-tui's types and read through a cast (pi transpiles extensions without type-checking), so a pi-tui rename would reintroduce the bug. `session-title.ts` needs a third way, because its delayed re-assert has to outlive the handler that scheduled it: it captures only `ctx.ui.setTitle`, which closes over the interactive mode rather than the session and so stays valid, and pairs it with a generation counter that drops a timer whose session has already been replaced.

`.pi/agent/skills/dnsimple/` searches for unregistered domain names through the DNSimple API v2 — `search` generates candidates (names × TLDs × prefixes/suffixes) and checks each, `check`/`prices`/`tlds`/`whoami` are thin wrappers. Dependency-free (Node's built-in `fetch`), so there's no install step. It needs a DNSimple **account** API token in `DNSIMPLE_TOKEN`, which belongs in `secrets.fish` (see Secrets below); set `DNSIMPLE_ACCOUNT` too and it skips the `/whoami` lookup. Two things to know before extending it: there is **no bulk availability endpoint** — `check` is one HTTP request per domain, and `checkDomain` carries its own quota of **60 checks per rolling 60 minutes** (the window starts at your first check, not on the hour) that no response header tracks (it returns 429 `endpoint checkDomain quota exceeded` while `x-ratelimit-remaining` still reads 2287 of the 2,400 account allowance), so broad sweeps fail partway and partial results are reported under `NOT CHECKED` — and the account id is cached as an **in-flight promise**, not a resolved value, because the checks run concurrently and caching only the result let every worker miss an empty cache and race its own `/whoami`, doubling request count. `node .pi/agent/skills/dnsimple/test.mjs` exercises the CLI against a self-terminating stub API via the `DNSIMPLE_API_BASE` override (no token, no network) and prints a request count at the end, which is what caught that stampede. `.pi/agent/skills/hig/` reads Apple's Human Interface Guidelines for Apple-platform UI work — `show` renders a page as markdown, `search`/`list` browse the catalog, `updated` reports which guidance recently changed. It's one of three skills shared with Claude Code (see `worktrunk` and `plane` below): the files live under `.pi/`, and `.claude/skills/hig` is a **repo-level symlink** to `../../.pi/agent/skills/hig` rather than a copy, which both `install-pi` and `install-claude` pick up because their `*/` globs match symlinked directories (`~/.claude/skills/hig` → repo `.claude/skills/hig` → `.pi/agent/skills/hig`). Dependency-free (Node's built-in `fetch`). The content comes from an **undocumented DocC JSON endpoint** — `developer.apple.com/tutorials/data/design/human-interface-guidelines/<slug>.json`, the data the HIG site's own renderer consumes — so pages arrive as structured content blocks and render to markdown without HTML scraping; if Apple ever drops it the failure is a 404 or an HTML body, both surfacing as "No HIG page". Nothing outside that section is filtered, and a footer names what was dropped. The page index costs ~172 requests (a BFS four levels deep that converges on 171 pages) and is built lazily on the first `search`/`list`/`updated`, so a plain `show` stays one request; caches live in `$TMPDIR/hig-cache` (pages 1 day, index 1 week) deliberately outside the repo so fetched pages never appear in `git status`. `node .pi/agent/skills/hig/test.mjs` runs the CLI against a stub API via the `HIG_API_BASE` override with no network, and the platform-filter cases are the ones worth keeping green.

`.pi/agent/skills/worktrunk/` teaches an agent to drive [worktrunk](https://github.com/max-sixty/worktrunk) — the `wt` CLI for git worktrees, aimed at running several agents in parallel. It's the second skill shared with Claude Code via the same repo-level symlink trick as `hig` (`.claude/skills/worktrunk` → `../../.pi/agent/skills/worktrunk`), so both hosts read one file. Prose only, no scripts, and it defers to `wt <command> --help` for flag detail rather than freezing a fast-moving CLI. It **replaces** a former Claude-only `worktree` skill (a `/worktree` command built on Claude's built-in `EnterWorktree` tool and plain `git worktree`), retired once `wt` was installed; recover it from git history if ever needed. Frontmatter on a shared skill stays at `name` + `description`, as `hig` does: the two hosts disagree past that point — Claude's `user-invocable` has no pi equivalent (pi uses `disable-model-invocation` and exposes `/skill:<name>` regardless), and `allowed-tools` is comma-delimited for Claude but space-delimited for pi. Both hosts auto-load on the description alone, so there's nothing to gain by picking a side. Worktrunk ships its *own* Claude Code plugin with a `/worktrunk` skill, but that one is about *configuring* worktrunk (LLM commits, hooks, shell integration) and is Claude-only — this one is about *using* it, and pi gets nothing from upstream (the plugin matrix covers Claude Code, Codex, OpenCode, and Gemini). The whole reason it exists as prose an agent must read is a set of traps that `--help` states nowhere: **`wt switch` cannot change an agent's directory** — the cd is performed by a *shell function* that reads a path worktrunk drops in `$WORKTRUNK_DIRECTIVE_CD_FILE`, so a non-interactive tool call never loads it and the cd would die with the subprocess anyway, making `--no-cd --format=json` → read `.path` → `-C <path>` the only reliable sequence; a bare `wt switch` (or `--branches`/`--remotes`/`--prs`) opens a **fuzzy picker** that hangs a tool call forever; project hooks demand **approval on first run**, which `wt config approvals list --format=json` reports without prompting and `-y` waives for a single run; `wt list --format=json` still emits the legacy **schema 1** bare array plus a warning unless the user's config opts into `json-schema = 2`, so the skill pins it per-call with `--config-set`; and `wt merge` is not `git merge` but a squash-rebase-fast-forward-then-delete-the-worktree pipeline, so it's flagged as confirm-first alongside `remove -f`/`-D`. The skill still opens by checking `command -v wt`, since it's shared with hosts on other machines.

`.pi/agent/skills/plane/` creates, lists, updates, comments on and closes work items on the self-hosted [Plane](https://plane.so) in the galactus homelab cluster — `projects`/`list`/`get`/`comments` to read, `create`/`update`/`assign`/`comment`/`close`/`delete` to write, `states`/`labels`/`members` to discover ids. Dependency-free (Node's built-in `fetch`). `.pi/agent/skills/skill-audit/` audits the skill catalog itself for routing ambiguity, through TypeSafe's System One API — `overlap` scores every pair of descriptions, `audit` runs a prompt file and reports mismatches, `route` dumps one probability distribution, `catalog` lists what was discovered without calling the API. Dependency-free (Node's built-in `fetch`); the key lives in `secrets.fish` as `TYPESAFE_API_KEY` (the name the official SDKs read, though the script also accepts `TYPESAFE_API_TOKEN`). It exists because an agent picks a skill from **name and description alone**, so two descriptions that read alike are a silent bug — nothing errors, the wrong skill just loads. That is the problem the `review`/`review-pr` split was solved by hand, and with 24 skills across two hosts nothing was re-checking it. `overlap` needs no test prompts: the catalog rides in `state`, which Jev ingests once and evaluates every question against, so all 276 pairs go out as parallel nouls batched 40 to a request and the whole matrix costs ~$0.002 and about 1.5 seconds rather than 276 round-trips.

Four things are load-bearing. The threshold is **0.75, not 0.5**: a noul at 0.5 is *maximum uncertainty* — equal probability for yes and no — not "medium overlap", so cutting there flags the model's shrugs and produced 58 hits out of 276, which is unusable. Skills carrying `disable-model-invocation` are **excluded by default**, because the model can never auto-pick them and counting them as conflicts is noise — `pr` alone contributed four phantom pairs; note that is the *hyphenated* key, and peon-ping's underscored `user_invocable` is a different thing that gates the **user**, not the model, so it is deliberately not treated the same. A flagged pair is a **lint, not a failure**: `overlap` measures whether two descriptions *could* be confused, and the worst pair here (`peon-ping-config`/`peon-ping-toggle` at 0.91, where toggle's description really does end by claiming "any peon-ping setting") still routes correctly and decisively on concrete prompts, 0.93 and 1.00 — so the SKILL.md says so outright rather than letting the number imply a broken catalog, and `audit` with real prompts is the ground truth. And a pair the API returned no answer for is reported as `NOT CHECKED` and exits non-zero, because an incomplete run silently reading as a clean bill of health is exactly how a commit gate goes green on work it never did.

Two traps are guarded because both were caught only by running it rather than reading it. `IS_MAIN` **realpaths both sides**: skills install as symlinks into `~/.pi/agent/skills`, so `argv[1]` is the link while `import.meta.url` is already resolved to the repo, and comparing them raw makes the guard false so the CLI prints *nothing* when run the only way it actually gets run — invisible from the repo path, which is why `test.mjs` invokes it through a symlink on purpose. And skill names are constrained to `[\w.-]` with control characters stripped from names and descriptions at the point they are read, because a name is interpolated into the model's **instruction** channel while a description is printed straight to the terminal, and the scanned directories hold brew-owned, npx-installed and externally managed skills — the same reasoning that keeps `todo-md.ts` from trusting a glyph out of a cloned repo's config. `node .pi/agent/skills/skill-audit/test.mjs` runs all 38 checks against a self-terminating stub of the System One endpoint and a fixture catalog in `$TMPDIR` — no key, no network, no model — including a hostile `SKILL.md` carrying `ESC ]0;` and a quoted newline in its name.

`brew "worktrunk"` is in the Brewfile, but the formula alone isn't enough: `wt switch` cannot change directories until `wt config shell install` has run, because the cd is performed by a shell function rather than the binary. That step needs care here — `~/.config/fish` is a **symlink to this repo**, so it writes `functions/wt.fish` and `completions/wt.fish` *into the working tree*. `functions/.gitignore` is an allowlist (`*` plus `!` exceptions for the functions we author), so the function file was ignored already; `completions/` had no `.gitignore` at all, so a matching allowlist was added there. Note the self-reference: an allowlist's own `*` matches `.gitignore`, and `functions/.gitignore` escapes that only because it was already tracked when the rule appeared — a *new* one silently ignores itself and never gets committed, which is why `completions/.gitignore` carries an explicit `!.gitignore`. Homebrew also drops a `wt` completion in `share/fish/vendor_completions.d`; the copy under `~/.config/fish/completions/` shadows it, which is the intended outcome — worktrunk's own function stub guards against recursing into a stale vendor completion. The formula conflicts with `wiredtiger` (both install a `wt` binary).

The vendored herdr control-skill (`.pi/agent/skills/herdr/SKILL.md`) teaches pi to *drive* herdr from inside a pane — spawn sibling panes with `--no-focus`, run commands/agents, `herdr wait agent-status`, read output. It's gated on `HERDR_ENV=1` (a no-op outside herdr) and defers to `herdr --help` for live CLI syntax, so it tolerates herdr upgrades. It's a copy of upstream; refresh with `curl -fsSL https://raw.githubusercontent.com/ogulcancelik/herdr/master/SKILL.md -o .pi/agent/skills/herdr/SKILL.md`.

`.claude/skills/review/` reviews the **current working tree** before landing it — fetch, diff against the merge base, report findings, stop. It pairs with `review-pr`, which reviews a PR or branch that is *not* the current tree; the split is stated in both descriptions so the model picks correctly rather than reviewing the session CWD when asked about a PR. It replaces gstack's `/review`, removed along with the rest of that collection (see below), and deliberately reuses that name — which was only safe *after* the gstack symlink at `~/.claude/skills/review` was gone, since `_link` skips when the target exists and would otherwise have reported "already exists, skipping" on every run while the tracked copy sat dead. Three things were worth keeping from the original and are the reason this exists rather than a bare "review my diff" prompt. Diffs are taken against `git merge-base origin/<base> HEAD` **after** an explicit `git fetch`, because a stale base invents findings about code that already landed. Findings must **quote the line that motivates them** — the fix for the dominant failure mode of automated review, a fluent, confident report about a field that does not exist; anything unquotable is dropped or listed as `Unverified` rather than laundered into a confidence score. And the suppression list is retained, since most of the noise in a review is style churn and "add a comment explaining this constant". Everything else went: the ~840-line platform preamble, ~44 `gstack-*` binary calls, and nine subsystems (specialists with hit-rate gating, Red Team, Greptile triage, Codex cross-model synthesis, plan-file scope drift, VERSION queue slots, `TODOS.md` cross-ref, doc staleness, learnings logging) — 1852 lines and 184K across 12 files became a single file of ~130 lines. It is also deliberately **report-only**, where the original auto-applied fixes mid-review: a skill named review should not mutate the tree, and merging *what was found* into *what was changed* makes both harder to audit. The categories were rewritten by bug class instead of the original's Rails/Python/LLM-app specifics, which gave Rust — a primary language here — zero coverage. One trap is called out in the file so it does not get "simplified" back: the base-branch fallback uses `${base#origin/}` and `${base:-main}` rather than `sed 's|^origin/||' || echo main`, because in a pipeline the exit status is `sed`'s, and `sed` succeeds on empty input — so the `||` never fires and a repo with no `origin/HEAD` silently gets an empty base. Step 1 also runs `git ls-files --others --exclude-standard` alongside the diff, because `git diff` reports **tracked** files only — a brand-new file appears nowhere in it, not even in `--stat`, so a review that trusts the diff alone will skip an entire new module and report clean on work it never read. That was caught by running the skill on the commit that introduced it, where the skill's own file was untracked and therefore invisible to itself.

The **gstack** skill collection (`~/.claude/skills/gstack`, a 1.0 GB clone of `github.com/garrytan/gstack` plus 28 symlinks into it, and a `~/.gstack` state dir) was removed. Claude Code history showed exactly one of its 28 skills had ever been invoked — `/review`, 48 times — and `~/.gstack/config.yaml` had already disabled its ambient behavior (`telemetry: off`, `proactive: false`, `update_check: false`, `routing_declined: true`). It is restorable with a re-clone if a capability is ever missed; `browse`/`qa`/`benchmark` (a headless-browser harness) and `ship`/`land-and-deploy` (release automation) are the substantial ones. Nothing was wired to it — no `settings.json` entries, hooks, plugins, PATH binary, launchd job, or Brewfile line — so removal was just unlinking.

`.claude/hooks/zellij-tab-notify.sh` puts a 🔔 on the zellij tab containing a Claude Code session that's waiting for input, and clears it when you respond. The script alone does nothing — it must be wired to hook events (`track` on SessionStart/UserPromptSubmit, `notify` on Stop/Notification/PermissionRequest, `clear` on PostToolUse/SessionEnd) in `~/.claude/settings.json`, which is not versioned here. It targets tabs via `rename-tab-by-id` (needs zellij ≥ 0.43) because plain `rename-tab` acts on the user's *focused* tab, which is the wrong tab exactly when the notification matters.

The Firefox `extensions/treestyletab/style.css` is not symlinked — it must be pasted into the Tree Style Tab options page manually.

## Architecture

**Fish is the primary surface.** The bulk of the customization lives under `.config/fish/`:

- `config.fish` — entrypoint. Defines `SCHEME_*` color variables (Monokai-derived), bootstraps `pyenv` / `rbenv` / `fzf` / `fisher`, sets `fish_color_*` globals, and prepends path entries to `fish_user_paths`. Fish 4.3+ no longer persists `fish_color_*` in universal scope, so they're set as globals here on every shell start.
- `fish_plugins` — fisher plugin manifest. Run `fisher update` after editing.
- `functions/fish_prompt.fish` — custom two-line prompt that consumes the `SCHEME_*` variables from `config.fish` via the `__print_color` helper.
- `functions/_env_hints.fish` — invoked from the prompt; surfaces active env context.
- `functions/git_*.fish` come from the `arbourd/fish-git-util` plugin (not custom).

**Plugin managers in play** — each owns its own install path:

| Tool | Manager | Manifest | Install path |
|---|---|---|---|
| fish | fisher | `.config/fish/fish_plugins` | `~/.config/fish/functions/` (mixed with custom functions) |
| vim | Vundle | `Plugin` lines in `.vimrc` | `~/.vim/bundle/` (gitignored) |

When adding a fish function, drop it in `.config/fish/functions/<name>.fish` — fish autoloads by filename. Functions prefixed `__` are internal helpers (e.g. `__print_color`, `__fzf_*`).

**Prompt color scheme** lives in two places that must stay in sync: `SCHEME_*` vars in `config.fish` (used by `fish_prompt.fish`) and the `fish_color_*` globals further down in the same file (used by fish's syntax highlighting).

**Secrets** go in `~/.config/fish/secrets.fish` — gitignored, sourced from `config.fish` if present. Use this for API keys, tokens, anything machine-specific. The file is optional; if it doesn't exist the source line is a no-op. Never commit secrets to `config.fish` directly.
