# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Install

Fresh machine, in order:

```sh
# Install `just` first — either via Homebrew (needs brew already) or directly:
curl --proto '=https' --tlsv1.2 -sSf https://just.systems/install.sh \
  | bash -s -- --to /usr/local/bin

just bootstrap                 # install Homebrew if missing, then brew bundle
just install                   # symlink dotfiles into $HOME
just bootstrap-plugins         # install fish/vim plugins
```

Or do one tool at a time: `install-{fish,vim,git,zed,zellij,claude,pi,herdr}` for symlinks, `bootstrap-{fish,vim,herdr}-plugins` for plugin managers, `bootstrap-herdr-integrations` for herdr agent hooks.

The plugin step **must** run after `install` — fisher reads `~/.config/fish/fish_plugins` and vim reads `~/.vimrc`, both from `$HOME` (via the symlinks `install` just created). `bootstrap-vim-plugins` also clones Vundle itself if missing.

All `install-*` recipes are idempotent — they **skip if the target path already exists**. The flip side is that a *real* file or directory sitting at a target silently wins forever: the recipe reports "already exists, skipping" on every run, and the tracked copy is dead weight that edits never reach. This had happened to the `github` pi skill, which sat in `~/.pi/agent/skills/` as a plain directory (identical in content, so nothing looked wrong). When adding something to this repo that already exists in `$HOME`, move the original aside first, then run the recipe, and `ls -la` the target to confirm it came out a symlink. `bootstrap` is also re-runnable. `bootstrap-plugins` is safe to re-run but does network I/O each time. Recipes call the internal `_link` helper (just `ln -s` with a skip-if-exists guard); edits to individual files go live immediately because the dotfiles are symlinked, not copied.

`install-zed` and `install-zellij` symlink individual files (`settings.json` + `themes/` for Zed; `config.kdl` + `layouts/` for Zellij) rather than the whole `~/.config/{zed,zellij}/` directory — both apps write runtime state (Zed: `conversations/`, `prompts/`; Zellij: `plugins/` with downloaded WASM binaries) into those directories and we don't want it leaking into the repo. `install-claude` follows the same pattern for `.claude/hooks/zellij-tab-notify.sh` and also loops over `.claude/skills/*/` to symlink the skills we author ourselves (currently `pr` and `worktree`) into `~/.claude/skills/` — `~/.claude/` is full of runtime state and other unversioned hooks, and `~/.claude/skills/` in particular mixes externally-managed collections (`gstack/`, `xcode/`) and brew-owned skills (`peon-ping-*`), so we only symlink our own. `install-pi` symlinks `.pi/agent/AGENTS.md` (global agent instructions), every skill directory under `.pi/agent/skills/` (currently `herdr`, `socratic-tutor`, `github`, and `dnsimple`), and every extension under `.pi/agent/extensions/` (currently `todo-md.ts`) into `~/.pi/agent/`, which otherwise holds runtime state (`auth.json`, `sessions/`, other unmanaged `skills/` and `extensions/`, `themes/`). The recipe loops over `.pi/agent/skills/*/` and `.pi/agent/extensions/{*.ts,*/}`, so tracking a new pi skill or extension is just dropping a `<name>/SKILL.md` dir or a `<name>.ts` file into the repo — no justfile edit needed (the `_link` skip-if-exists guard keeps it idempotent). The extension loop is deliberately scoped to files present in *this repo*: `~/.pi/agent/extensions/` also holds `herdr-agent-state.ts` (generated by herdr, see below) and other unversioned extensions, which must not be clobbered. `install-herdr` symlinks only `.config/herdr/config.toml` — `~/.config/herdr/` also accumulates runtime logs (`herdr.log`, `herdr-client.log`, `herdr-server.log`).

`.config/herdr/plugins/tab-jump/` is a herdr plugin (herdr ≥ 0.7.4 has a plugin system: `herdr plugin link|install|list|action|pane`, manifest `herdr-plugin.toml`) that replaces the zellij `room.wasm` binding — fuzzy-search every tab in the session and jump to it. `just bootstrap-herdr-plugins` registers it; the recipe loops over `.config/herdr/plugins/*/` and skips anything already in `herdr plugin list`, so adding a plugin is just dropping a `<id>/herdr-plugin.toml` dir into the repo. Unlike everything else here it is **not** symlinked — `herdr plugin link` writes the absolute path into `~/.config/herdr/plugins.json`, so the registration points straight at this repo and edits to `jump.sh` are live. The manifest's `id` must match the directory name for the bootstrap recipe's skip-check to work.

The plugin has two halves: a `[[panes]]` entrypoint (`placement = "popup"`, a session-modal float that leaves the workspace layout alone — the analogue of zellij's `floating true`) and a `[[actions]]` entrypoint that opens it, bound to `prefix+y` in `config.toml` via `[[keys.command]]` with `type = "plugin_action"`. The key can't point at the pane directly; `plugin_action` is the only plugin-aware keybind type, so the action shells out to `herdr plugin pane open`. `[[keys.command]]` blocks must stay at the *end* of `config.toml` — TOML would fold any later bare key into the command table instead of `[keys]`. Commands reach their own files through `$HERDR_PLUGIN_ROOT` rather than a hardcoded path, and the `herdr` binary through `$HERDR_BIN_PATH`.

`jump.sh` reads one `herdr api snapshot` and renders a row per tab (agent status dot, `<workspace#>.<tab#>` quick-jump token, `workspace › tab`, the agent's terminal title, cwd), pipes it through `fzf` with a live `herdr pane read` preview, then focuses the choice. Two non-obvious constraints. The tab and pane ids ride along as hidden TSV fields (`--with-nth=1`) because the visible text is unstable. And the `herdr tab focus` call must happen *after* the popup is torn down — the teardown restores focus to the previously active pane, which would undo the jump — so it runs in a backgrounded child guarded by **`set -m`**. That is load-bearing: a plugin pane's process is a session leader and herdr kills its entire process group on close, so a plain `... &` from a non-interactive shell stays in that group and is killed before it ever runs (this silently broke the first version — the picker worked, selection parsed, nothing jumped). Job control is what puts the child in its own process group. The child also *verifies* rather than retrying on error, since `tab focus` returns success even when the teardown immediately steals focus back.

A plugin pane's stderr dies with its pty and never reaches `herdr plugin log list` (that only captures `[[actions]]`), so `jump.sh` has an opt-in trace: `herdr plugin pane open --plugin tab-jump --entrypoint picker --env TAB_JUMP_DEBUG=1` writes a `set -x` log to `$TMPDIR/tab-jump.log`. Note that a popup opened with `--no-focus` is keyboard-inert but still occupies the single popup slot, so subsequent opens fail with `popup already open`; plugin panes are invisible to `herdr api snapshot` and `pane list`, and `plugin pane open` does not return their id, so the only way to clear a wedged one is to `kill` the `jump.sh` pid from `ps`. herdr's own `goto` (`prefix+g`) covers similar ground but enumerates every pane, which is too noisy.

The herdr↔agent state integrations (pi/claude/codex lifecycle hooks that report `idle`/`working`/`blocked` and enable native session restore) are generated *outside* this repo by herdr, so they're not symlinked. Run `just bootstrap-herdr-integrations` to (re)install them via `herdr integration install` — safe to re-run, and it re-syncs versions after a herdr upgrade (`herdr integration status` shows current/outdated). herdr and pi are not in the Brewfile yet, so a fresh machine needs them installed first.

`.pi/agent/extensions/todo-md.ts` is a pi extension giving every repo a persistent task list backed by a plain `todo.md` at the git root. It registers a `todo` tool (`list`/`add`/`toggle`/`remove`/`clear_done`) for the agent, a `/todos` overlay (plus `/todos hide|show`), and an always-on widget above the editor that lists open items and auto-hides when the list is empty or fully done — so repos without a `todo.md` see nothing. It is a file-backed rewrite of pi's bundled `todo.ts` example (`$(brew --prefix)/lib/node_modules/@earendil-works/pi-coding-agent/examples/extensions/todo.ts`), which stores state in session entries instead; that makes the bundled version rewind correctly when you branch a session, but it does not survive across sessions, which is the whole point here. Non-checkbox lines in `todo.md` (headings, prose, notes) round-trip verbatim and new items are inserted after the last existing checkbox, so the file stays hand-editable. Todo ids are positional and shift after `remove`/`clear_done`, so every tool result returns the refreshed list. Extensions in `~/.pi/agent/extensions/` are auto-discovered and hot-reload with `/reload`.

All pi extension event handlers must use the `ctx` passed *into* the handler rather than capturing one from an enclosing scope — pi invalidates `ctx` on session replacement and every getter on the stale object throws. `pi.on()` has no unsubscribe, so handlers outlive their session. `todo-md.ts` sidesteps this by only ever using the handler's own `ctx`; the (unversioned) `border-status-editor.ts` has to work around it with a generation counter because it captures `ctx` for a custom editor component.

`.pi/agent/skills/dnsimple/` searches for unregistered domain names through the DNSimple API v2 — `search` generates candidates (names × TLDs × prefixes/suffixes) and checks each, `check`/`prices`/`tlds`/`whoami` are thin wrappers. Dependency-free (Node's built-in `fetch`), so there's no install step. It needs a DNSimple **account** API token in `DNSIMPLE_TOKEN`, which belongs in `secrets.fish` (see Secrets below); set `DNSIMPLE_ACCOUNT` too and it skips the `/whoami` lookup. Two things to know before extending it: there is **no bulk availability endpoint** — `check` is one HTTP request per domain against a 2,400/hour account limit, so a 10-name × 10-TLD search costs 100 requests — and the account id is cached as an **in-flight promise**, not a resolved value, because the checks run concurrently and caching only the result let every worker miss an empty cache and race its own `/whoami`, doubling request count. `node .pi/agent/skills/dnsimple/test.mjs` exercises the CLI against a self-terminating stub API via the `DNSIMPLE_API_BASE` override (no token, no network) and prints a request count at the end, which is what caught that stampede. Registration is deliberately not implemented; it's a `POST` that spends money.

The vendored herdr control-skill (`.pi/agent/skills/herdr/SKILL.md`) teaches pi to *drive* herdr from inside a pane — spawn sibling panes with `--no-focus`, run commands/agents, `herdr wait agent-status`, read output. It's gated on `HERDR_ENV=1` (a no-op outside herdr) and defers to `herdr --help` for live CLI syntax, so it tolerates herdr upgrades. It's a copy of upstream; refresh with `curl -fsSL https://raw.githubusercontent.com/ogulcancelik/herdr/master/SKILL.md -o .pi/agent/skills/herdr/SKILL.md`.

`.claude/hooks/zellij-tab-notify.sh` puts a 🔔 on the zellij tab containing a Claude Code session that's waiting for input, and clears it when you respond. The script alone does nothing — it must be wired to hook events (`track` on SessionStart/UserPromptSubmit, `notify` on Stop/Notification/PermissionRequest, `clear` on PostToolUse/SessionEnd) in `~/.claude/settings.json`, which is not versioned here. It targets tabs via `rename-tab-by-id` (needs zellij ≥ 0.43) because plain `rename-tab` acts on the user's *focused* tab, which is the wrong tab exactly when the notification matters.

The Firefox `extensions/treestyletab/style.css` is not symlinked — it must be pasted into the Tree Style Tab options page manually.

## Architecture

**Fish is the primary surface.** The bulk of the customization lives under `.config/fish/`:

- `config.fish` — entrypoint. Defines `SCHEME_*` color variables (Monokai-derived), bootstraps `pyenv` / `rbenv` / `fzf` / `fisher`, sets `fish_color_*` globals, and prepends path entries to `fish_user_paths`. Fish 4.3+ no longer persists `fish_color_*` in universal scope, so they're set as globals here on every shell start.
- `fish_plugins` — fisher plugin manifest. Run `fisher update` after editing.
- `functions/fish_prompt.fish` — custom two-line prompt that consumes the `SCHEME_*` variables from `config.fish` via the `__print_color` helper.
- `functions/_env_hints.fish` — invoked from the prompt; surfaces active env context.
- `functions/git_*.fish` come from the `arbourd/fish-git-util` plugin (not custom).

**Plugin managers in play** — each owns its own install path:

| Tool | Manager | Manifest | Install path |
|---|---|---|---|
| fish | fisher | `.config/fish/fish_plugins` | `~/.config/fish/functions/` (mixed with custom functions) |
| vim | Vundle | `Plugin` lines in `.vimrc` | `~/.vim/bundle/` (gitignored) |

When adding a fish function, drop it in `.config/fish/functions/<name>.fish` — fish autoloads by filename. Functions prefixed `__` are internal helpers (e.g. `__print_color`, `__fzf_*`).

**Prompt color scheme** lives in two places that must stay in sync: `SCHEME_*` vars in `config.fish` (used by `fish_prompt.fish`) and the `fish_color_*` globals further down in the same file (used by fish's syntax highlighting).

**Secrets** go in `~/.config/fish/secrets.fish` — gitignored, sourced from `config.fish` if present. Use this for API keys, tokens, anything machine-specific. The file is optional; if it doesn't exist the source line is a no-op. Never commit secrets to `config.fish` directly.
